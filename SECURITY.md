# Security policy

Nexus SymBiote is alpha security tooling. Inventory, signature verification, and policy decisions have different meanings. A successful scan or low risk score does not establish that an agent, model, dataset, or tool is benign.

## Reporting a vulnerability

Report security-sensitive defects through the repository's **Security > Report a vulnerability** feature: [open a private report](https://github.com/Hunzee-VC/Nexus-Symbiote/security/advisories/new). Private vulnerability reporting is enabled for this repository; the report reaches the repository's administrators and stays private until an advisory is published. Do not put credentials, private BOMs, exploit details, or customer data in a public issue.

Include the affected commit or distribution version, platform and Python version, reproduction steps with synthetic inputs, expected and observed behavior, and the trust boundary crossed. Keep real credentials and sensitive agent context out of reproduction artifacts.

**What to expect.** The project has one maintainer and offers best effort, not a service level: an acknowledgement within 7 days, and coordinated disclosure 90 days after the report by default, or earlier once a fixed version is published. The reporter and the maintainer can agree on another date. Fixes ship as a new version, and the advisory names the affected and fixed versions.

**If nobody answers.** There is no second security contact yet ([continuity](GOVERNANCE.md#continuity)). If a private report has no acknowledgement after 7 days, open a public issue titled "Security report awaiting acknowledgement" that gives the report's date and nothing about its content. If the form itself is unavailable, open such an issue asking for a private channel instead; never put details in it.

**Scope.** A way to make a documented guarantee fail is in scope: a gate that passes when it should fail, collection that reads, executes or reaches the network where the documentation says it does not, a secret that reaches an inventory, log or export, or terminal or CI output an input can steer. The items under [known limitations](#known-limitations-in-010) are tracked publicly; a new consequence of one, such as a bypass the entry does not describe, is still worth a private report.

## Supported versions

Only the latest reviewed alpha revision is developed. There is no long-term support commitment or established production support window. Confirm release provenance and the matching source revision before installing a published distribution.

## Imported discovery evidence

Treat ShadowScan reports, CycloneDX imports, A2A cards, IDE settings, and extension manifests as untrusted inputs. A discovery record does not grant authority or authenticate the discovered endpoint. Verify the expected subject, signer, tenant, time, and policy before upgrading a claim. Never grant deployment or publication credentials to the import job merely to parse a report.

To require that a merged inventory's ShadowScan evidence comes from a signed report, name the report in an operator signature policy kept outside the checkout and pass it to `validate --project` or `risk --project` ([require a signed report in CI](docs/shadowscan-integration.md#require-a-signed-report-in-ci)). Setting `validate.require_discovery_signature: true` in the project policy also turns the check on. The content digest that `diff` compares detects drift; it does not authenticate a report.

## Security boundaries

Static collection must not execute project modules, model loaders, repository hooks, or MCP launch commands. Treat repositories, model files, tool metadata, registry records, and imported BOMs as hostile input. Run scans with read-only access and without deployment or publication credentials.

Every bound on what a scan reads fails closed. The [collection limits](docs/collection-limits.md) are operator settings, changed only with `--limit` or `NEXUS_SYMBIOTE_LIMITS`; nothing in the scanned checkout can change them. TypeScript MCP server files are parsed inside the scanning process by tree-sitter, which is native code. Size, node and time bounds limit that parse but do not isolate it, so a memory-safety defect in the parser would run with the scan's privileges.

Confined file operations and pinned stdio launchers require POSIX descriptor-relative and no-follow primitives. Unsupported platforms fail closed rather than weakening those checks. Hard links are regular files: a hard-linked file inside the scanned root is read and hashed like any other, so an inventory can describe an inode that also has a name outside the root. Run static collection with the content author's privileges rather than as root, on hosts with `fs.protected_hardlinks=1`, and extract untrusted archives with a tool that refuses link targets outside the destination (GNU tar, or Python `tarfile` with `filter='data'`). The configured hosted matrix targets Ubuntu with Python 3.11 through 3.14; it does not qualify macOS or Windows support.

`verify-live` is an explicit execution operation. Its operator-owned launch policy must be outside the scanned project and binds exact server references to independently obtained executable SHA-256 pins. It stages the approved bytes privately, passes no project arguments, clears inherited environment variables, uses a private working directory and terminates the process group after bounded protocol collection. It invokes no tools. Launcher pins do not authenticate the OS, interpreter, linked libraries or other host dependencies. Execute launchers in an externally isolated worker with resource limits and restricted filesystem, identity and network access. `--record` emits a separate unsigned candidate, not an approval or admission decision; incomplete observations and missing tools fail closed, and changed or new tools, server declarations or server identity make it exit 1 unless `--accept-drift` is given. `verify-live` does not verify servers reached over HTTP; observe them with `discover-mcp --record` and compare the inventories with `diff`.

A signature proves that authorized key material signed particular bytes under the verifier's policy. It does not prove that the content is accurate or safe. A matching tool descriptor cannot prove that the backend behaves as declared. Enforcement integrations govern only calls actually mediated by those integrations.

Agent inventories can expose infrastructure, permissions, endpoints, and instruction fingerprints. Restrict access to exported evidence and review its contents before sharing it. Keep raw credentials out of BOMs, logs, and issue reports.

## Known limitations in 0.1.0

The pre-publication review of 0.1.0 confirmed these gaps. When a scan meets one of the detection gaps below, it still reports complete coverage, and neither `validate`, `risk` nor `diff --fail-on-alert` can flag what the inventory does not record, so review changes to those files by other means until a later release covers them.

- **Claude Code and other IDE agent settings.** From `.claude/settings.json` and `.claude/settings.local.json`, and from copies in a subdirectory, which a host started there applies, including copies read through a `.claude` directory symlink (another spelling of `.claude` or of either file name in a subdirectory is a collection failure), the inventory records the permission mode, the number of allow, ask and deny rules, the number of hook handlers per event, and an RFC 8785 digest of each file (`settings_hashes`). A Claude Code plugin repository's `.claude-plugin/plugin.json`, `.claude-plugin/marketplace.json` and `hooks/hooks.json` are digested the same way. A changed value anywhere in those files, such as an added hook command or a removed deny rule, changes the record and raises a medium `properties changed` alert; reordered keys and whitespace do not. The rules and hook commands themselves are not recorded, so the alert says that a settings file changed, not what changed. Without `NEXUS_SYMBIOTE_SOURCE_BINDING_KEY` each digest covers the file as read, so anyone holding the BOM can confirm a guess of a whole settings file. With the key, each digest covers the file after the standard redaction and with environment variable names only, and `static_value_binding`, an HMAC under the key, binds every value as read; a value the redaction leaves in place, such as a password pasted into a hook command, can still be confirmed from the digest, so keep credentials out of settings files. Findings cover the `bypassPermissions` (high) and `acceptEdits` (medium) starting modes, hook commands, `apiKeyHelper` and `enableAllProjectMcpServers` (medium), plugins and marketplaces and `permissions.additionalDirectories` (low), and blanket grants (medium): rules with no specifier, or one made only of wildcard and root characters such as `Bash(**)` or `Edit(//**)`, for the shell, edit, write and web-fetch tools, whole MCP servers, and root-wide `Read` rules. Effective permissions across user and managed settings, workspace trust and session flags are not resolved. For other IDE agents the inventory records which marker files exist, the same digest of `.cursor/settings.json`, `.windsurf/settings.json`, `.cline/settings.json`, `.codex/config.json`, `.cursor/hooks.json` and `.gemini/settings.json`, and, only from an `agent.permissionMode` key in the first four, a permission mode, scored as for Claude Code. Codex `.codex/config.toml` is read for `approval_policy` and `sandbox_mode`, which are scored, but not digested; the `mcp` collector inventories the MCP servers declared there and in Gemini CLI `.gemini/settings.json`. Hook commands in Cursor `.cursor/hooks.json` are counted and reported as a medium finding. No mode is read for Copilot or Gemini CLI.
- **Instruction files outside the supported locations.** The `prompt` collector reads the fixed instruction files the README lists, `CLAUDE.md` and `AGENTS.md` in any subdirectory, every file in the rule, prompt and subagent directories it lists (including a `.clinerules` directory), and the files that the root `CLAUDE.md`, `.claude/CLAUDE.md`, `CLAUDE.local.md` and `GEMINI.md` import with `@path`, to five hops, including the imports of an imported file that it also records under its own name, such as `AGENTS.md` or a nested `CLAUDE.md`. The imports of a nested `CLAUDE.md` that no root memory file imports are not followed. An import that leaves the project root (a home-relative, absolute or drive path, or one that climbs above the root, with or without a file suffix and with either separator), that names an excluded path such as `node_modules`, or that lies deeper than the collection depth limit is a coverage gap, so write path aliases such as `@/components` as code. An import is resolved as hosts resolve it, collapsing `.`, `..` and repeated separators, before any limit applies; one with a backslash is also looked up as a Windows host reads it, with the backslash as a separator; and one whose resolved path is longer than 4,096 bytes or has a name longer than 255 bytes is a coverage gap. An import of a file the checkout does not contain is ignored, as is a token with a NUL character, and `@` words inside code are not imports. More than 5,000 distinct import targets in one project is a collection failure. Nested `CLAUDE.md` and `AGENTS.md` files are matched by their exact names; other nested names, such as `CLAUDE.local.md`, `GEMINI.md` or a `.cursorrules` below the root, other spellings of nested names, and other hosts' conventions are neither inventoried nor checked for hidden characters unless an [`agent.yaml` manifest](docs/agent-manifest.md) lists them. A nested instruction file in test fixtures or vendored code is inventoried, and its hidden characters reported, like any other; leave such directories out with `scan.exclude_paths`.
- **Skills, commands and subagents.** Every file in `.claude/skills`, `.claude/commands`, `skills`, `.agents/skills`, `.github/skills`, `.cursor/skills`, `.gemini/skills`, `.cursor/commands` and `.gemini/commands` is inventoried by digest, including files outside a directory that holds a `SKILL.md`: declarations (`.md`, `.mdc`, `.markdown`, `.txt`, `.yaml`, `.yml`, `.json` and `.toml` files) as type `skill`, and scripts and other resources as type `skill-resource`. Each is checked for hidden characters when it is UTF-8 text. A declaration above the 4 MiB read limit is a coverage gap; a resource above it is streamed within the collection's byte budget, digested, and checked for hidden characters as it streams when it is UTF-8 text. Front matter such as `allowed-tools` is not interpreted.
- **Hidden-character detection is character-based.** It reports every format character (Unicode category Cf), variation selectors and blank fillers such as U+180E and U+3164: bidi embedding, override and isolate controls and tag characters as critical, the LRM, RLM and ALM marks as medium, and the others as high. A zero-width joiner between pictographs, a presentation selector after a pictograph or a keycap base, the England, Scotland and Wales flag sequences and a leading byte-order mark are not reported; pictographs are recognised by code-point ranges. Lookalike letters are not detected. HTML and Markdown comments, hidden when rendered, are a low `hidden_markup` finding that reports their count, not their text.
- **Case variants and symlinks.** When a fixed path such as `CLAUDE.md`, `.mcp.json` or `.claude/settings.json` is absent, a file whose name differs only by case or Unicode normalisation, which case-insensitive file systems open instead, is a collection failure; when both exist, only the exact name is read. The same holds below an in-root directory symlink such as `.claude -> config/claude`, and for another spelling of a RAG configuration name, an A2A card path or nested Claude Code settings. The search lists directories within the collector's entry limit; more than 16 names in one directory that differ from a searched name only by case or normalisation are a collection failure, and so is the search beyond the entry limit, after which no further path is searched. A relative symlink whose target, resolved lexically, is a regular file or directory in the project, not excluded, no deeper than the walk depth limit and reached without another symlink, is read through its target, and `validate --project` hashes the same target; a read through a symlink to the project root, such as `.claude -> .`, and every other symlink are collection failures. A walk of the whole project skips directory symlinks, whose targets it walks under their own names, and looks up nested Claude Code settings below a `.claude` symlink and A2A cards below a `.well-known` symlink through the link. A walk of a rule, prompt, subagent, skill or command directory walks a directory symlink that leads elsewhere in the project once, under its target's name, and fails one to the project root or to a directory that holds the walked one.
- **Default exclusions match by name.** Any path component named `.git`, `node_modules`, `__pycache__`, `.venv` or `venv` is skipped everywhere, including inside agent-configuration directories, so `.claude/skills/venv/SKILL.md` is not inventoried. The patterns appear under `exclusions` in the BOM but are not reported as a coverage gap, and standard exports keep coverage `unknown` for them, as bare names or as `**/name`. Any other exclusion entry, including another spelling such as `./node_modules`, makes coverage `incomplete`.
- **Standard fields carry coverage only coarsely.** CycloneDX `compositions` and SPDX relationship `completeness` say only `incomplete`, or `unknown` (`noAssertion` in SPDX); no export says `complete`. Which collectors ran, what failed and what was excluded are only in the native extension. An SPDX export with no native-edge relationships states its coverage only in the free-text document `comment`; license relationships carry no `completeness`. cyclonedx-python-lib 11.12.0 drops `compositions` when it reserializes a BOM. That removes an `incomplete` warning, and SymBiote recovery then rejects the document; dropping an `unknown` composition removes no assertion, so that document still recovers. The CycloneDX `nexus-symbiote:dependency:relationship` property is an extension, not a standalone edge source: it marks a conditional edge only with `"conditional": true`, and in CycloneDX the condition text, like the edge's assurance level, is only in the embedded native document.
- **Exports from builds before 0.1.0 may not recover.** Exports declare the projection version that produced their standard fields, and 0.1.0 exports, which declare none, recover against the 0.1.0 projection. CycloneDX and SPDX exports written by earlier builds can fail recovery, because their standard fields match neither projection. `allow_legacy_relationships=True` recovers only a CycloneDX export with the exact historical edge projection, every relationship in `dependsOn` and no `conditional` flag, and still checks the coverage composition. Regenerate other exports from the native AIBOM or by rescanning; see [fingerprint migration](docs/fingerprint-migration.md#standard-projection-versions).
- **Model content.** OpenSSF Model Signing signatures (DSSE bundles) are not verified; pin the weight files or sign each one with a Sigstore message signature in the operator policy instead. A Sigstore entry without `expected_sha256` accepts any artifact its identity signed, such as an older release, so pin the digest when that matters. Keras, HDF5, SavedModel, TFLite, Core ML and ExecuTorch files are rated unknown without inspecting their layers or operations, which the default risk gate passes as high findings. Pickles under names other than the listed suffixes, and NumPy `.npy` and `.npz` arrays, are not inventoried. GGUF chat templates are checked only for known sandbox-escape shapes, and Hugging Face chat templates are digested but not inspected ([model integrity](docs/model-integrity.md)).
- **MCP server source forms.** Python servers are collected when `FastMCP` is imported by name from `mcp.server`, `mcp.server.fastmcp`, `mcp.server.fastmcp.server`, `fastmcp`, `fastmcp.server` or `fastmcp.server.server`, or `MCPServer` from `mcp.server.mcpserver`. The low-level `Server` from `mcp.server` or `mcp.server.lowlevel`, a constructor given `tools=` or `**` arguments, a server object used other than through its decorators and its run and settings attributes (for example passed to a helper), an aliased or subclassed factory, a classmethod constructor such as `FastMCP.from_openapi`, and `.tool` decorators on a server imported from another module are reported as gaps. Python files that name neither `mcp` nor a supported agent framework are not examined, and an MCP server or agent framework import spelled only with compatibility characters is reported as a gap. Among TypeScript and JavaScript servers, only `.ts` files with a named `McpServer` import are collected; JavaScript servers (`.js`, `.mjs`, `.cjs`), namespace imports (`import * as sdk`), `require` and `.mts` or `.cts` files are skipped without a gap. Server source under directories named `build`, `dist`, `test`, `tests`, `docs`, `benchmarks` or `examples` (and `__tests__` for TypeScript) is skipped without a gap.
- **MCP client files and launchers.** MCP client files are read at the project root: `.mcp.json`, `mcp.json`, `claude_desktop_config.json`, `.cursor/mcp.json`, `.claude/mcp.json`, `.vscode/mcp.json`, `.gemini/settings.json`, `.roo/mcp.json`, `.kiro/settings/mcp.json`, `.amazonq/mcp.json`, `.windsurf/mcp.json`, `.cline/mcp.json` and `.codex/config.toml`; and, in any subdirectory, files named `.mcp.json`, `mcp.json`, `mcp-config.json`, `mcp_config.json`, `mcp-servers.json`, `claude_desktop_config.json` or `cline_mcp_settings.json`, such as `packages/agent/.mcp.json`, `packages/agent/.vscode/mcp.json` and `.windsurf/mcp_config.json`. Every MCP configuration file is read for both its `mcpServers` and `servers` maps (a server named in both is a collection failure), a VS Code file, nested or not, as JSONC; Gemini CLI settings are read for `mcpServers` and Codex configuration for `mcp_servers` only. A file with one of those names that is not valid JSON (or JSONC, for VS Code), or whose server map is not a map of server objects, is a collection failure even when it is not an MCP configuration; leave it out with `scan.exclude_paths`. User-level client settings and MCP servers declared in application code (such as `MCPServerStdio(params=...)` or `StdioServerParameters(command=...)`) are not inventoried and leave no gap; Zed `context_servers`, opencode `mcp`, `.continue/mcpServers/` and `.junie/mcp/mcp.json` are reported as gaps without being parsed. A server field the collector does not interpret is a gap. Launchers are classified for `npx`, `npm exec`, `pnpm dlx`, `yarn dlx`, `bunx` and `bun x`, `uvx` and `uv tool run`, `uv run --with`, `pipx run`, `docker`, `podman` and `nerdctl run`, `deno run` and `go run`, also behind `env`, `sh -c` (with the options a shell reads after `-c`), `cmd /c` (also `/k`, `/r` and a switch glued to the command), `powershell -Command`, `wsl`, or `op`, `doppler`, `infisical`, `dotenvx` and `aws-vault` with `--`; a runner option the collector does not know, `npm --call`, an inline shell script, an `env -S` value with escapes, quotes, `${...}` or `#`, inline interpreter code (`node -e`, `tsx -e`, `ts-node -e`, `python -c`, `deno eval`), a git source without a full commit, URL or local path, or a runner the grammar does not classify (`dnx`, `jbang`, `pip-run`, `nix run`, `dotnet tool`, `gem exec`, `pixi exec`, `corepack`, `mise`, `pkgx`, `finch`, Apple `container`, `apptainer`) is a high `launcher_identity` finding and a gap. Any other command is recorded as a local executable by its basename with no gap, unless its arguments, or those a runner passes to the program or package it starts, name a package runner, shell or wrapper followed by words that start it (after the runner's own options; npm subcommands are resolved as npm resolves aliases and prefixes, and a Deno script, a container plugin or a `name@version` program name counts), or run inline interpreter code: an unrecognised wrapper such as `nice`, `sudo`, `cross-env` or a gateway package may run them, so that is a gap as well. An argument value that merely reads like such a launch (a prose argument containing `npx something`) is also a gap. A command whose directory names contain spaces is classified by its basename only when a shell reading of the same text cannot start anything else; otherwise it is a gap. Package resolver settings are read from `.npmrc` (as npm reads it), `bunfig.toml`, `.yarnrc.yml`, `.yarnrc`, `.env.yarn`, `uv.toml` and the `[tool.uv]` table of `pyproject.toml` at the project root only, for the runners that read them; npm `call` and `package` settings, from `.npmrc` or `npm_config_*` variables, and Yarn `yarnPath`, `plugins` and `yarn-path` make the launcher identity unknown; a server that runs in another working directory (`cwd`, `env -C`, `pwsh -WorkingDirectory`, `wsl --cd`, `uv --directory` or `--project`, `deno --config`), or that a configuration file below the root declares, has its package identity withheld instead, because that directory may hold resolver files of its own. User and global resolver configuration is not inspected, and neither are variables loaded from an `envFile` or by `dotenvx`, `doppler`, `infisical` or `op run --env-file`: a launched registry package then carries `environment-file=[unresolved]` instead of its identity.
- **Agent framework tool forms.** Python tools are collected from module-level functions decorated with `@tool` imported by name from `langchain_core.tools`, `langchain.tools`, `crewai.tools`, `smolagents` or `smolagents.tools`, with `@function_tool` from `agents` or `agents.tool`, and with `@<agent>.tool` or `@<agent>.tool_plain` on a module-level `Agent(...)` imported from `pydantic_ai` or `pydantic_ai.agent`. The name is the function name or a constant `name`, `name_or_callable` or `name_override` argument; the descriptor itself is not collected. A decorated function that is not at module level, a rebound decorator or agent, a qualified import such as `import langchain_core.tools`, and a star import are reported as gaps. Class-based tools, such as `BaseTool` subclasses and `StructuredTool.from_function`, are neither collected nor reported.
- **MCP values without a binding key.** Launch arguments, environment and header values are exported only as redacted positions and names, and endpoint and package index URLs as origins; the unkeyed `static_config_hash` covers only that exported structure. Without `NEXUS_SYMBIOTE_SOURCE_BINDING_KEY`, a changed launch argument other than the recorded launcher package (a served directory, a container mount, a flag, or a URL a package receives), a changed environment or header value, a path or query change of an endpoint or package index on the same host, a changed project resolver setting value, or a changed directory of a command whose basename is unchanged raises no alert. Such a server carries `source_values_bound: false` and a low `completeness` risk that names the key. It is a risk, not a coverage gap: gates on coverage do not fail on it and one alone passes the default risk gate, but each adds 1 to the aggregate score, so about ten such servers add 10 points toward the default fail threshold of 50 unless the key is set. A tool's `definition_hash` is an unkeyed digest of the original declared descriptor, including literals and text that the exported descriptor omits, so anyone holding the BOM can confirm a guess of a low-entropy value withheld there.
- **Source collection is bounded by size.** While looking for MCP, A2A and RAG references, each collector reads at most the `source-scan-bytes` [collection limit](docs/collection-limits.md) of source text, 64 MiB by default. Past that it records one coverage gap, naming the first file it did not read in full, and reads no further, so the scan fails its gate; leave generated or vendored trees out with `scan.exclude_paths`, or raise the limit. For MCP, only a file that names a supported SDK or agent framework is parsed, wherever it is, and one above the `syntax-bytes` limit (256 KiB by default) is a coverage gap of its own. The A2A and RAG Python heuristics read only files that name the SDK or a vector-store library and skip one they cannot read, decode or parse, or that is above 262,144 characters; for A2A, such a file that names `AgentCard` is a coverage gap, and so is an agent card built in Python. The A2A search skips directories named `tests`, `test`, `dist`, `build`, `docs`, `benchmarks` and `examples`.
- **Lockfiles.** The `registry` collector reads `npm-shrinkwrap.json` (which npm installs from instead of `package-lock.json`), `package-lock.json`, `pnpm-lock.yaml`, `yarn.lock` (v1 and Berry), `uv.lock` and `poetry.lock` in the project root, and only for AI packages declared in the root manifests. With the lockfiles of more than one package manager (npm, pnpm, Yarn), or with both Python lockfiles, no lockfile evidence is bound and the conflict is reported as an exclusion. A resolved version, integrity value or origin is a declared claim: nothing is fetched or verified. Python lockfiles yield the version, the index origin and the lockfile's own digest, not artifact digests. An npm, pnpm or Yarn integrity value without a SHA-256, SHA-384 or SHA-512 hash, such as Yarn v1's `sha1-`, is a collection failure, and so is a download URL that is not `https` or that a WHATWG URL parser could read as another host; Yarn Berry `checksum` values are not recorded. A `pnpm-lock.yaml` with anchors, aliases or tags, or with more than 1,000,000 YAML tokens, and a `uv.lock` or `poetry.lock` with a dotted key of more than 16 dots, are collection failures.
- **Registry manifests.** The `registry` collector reads the root manifests by pip 26.3's and BuildKit's parsing rules, but runs neither and fetches nothing. It inventories only the packages and images in its [AI package catalog](docs/registry-collector.md#ai-package-catalog): any other dependency, including a look-alike of a listed name, produces no component and no finding. An include, constraints file or editable install that reaches beyond the root `requirements*.txt` files or the project itself, and a URL, VCS, archive or path requirement without a package name, other than the project itself, is a coverage gap. A `name @ URL` requirement, including a VCS or `file:` URL outside the project, is inventory recorded by its name and URL origin (a URL without `//`, such as `file:../pkg`, is recorded as written), with no gap unless pip could read its text as a path in the project; a bare archive that starts with an AI package name is also recorded, under a mangled name (`openai-1.0.0.tar.gz` becomes `openai-1-0-0-tar-gz`), and a bare path such as `torch/` is recorded under its name with a collection failure (`invalid or unsupported PyPI requirement`). These are not reported:
  - images named outside `FROM`, such as `COPY --from=<image>` or `RUN --mount=...,from=<image>`;
  - options that follow a requirement on the same line, other than `-e` and `--hash` (whose values are recorded), and `${NAME}` variables inside them (a bare `${NAME}` word after a requirement makes the line an invalid requirement, which is a collection failure);
  - a `${NAME}` variable inside a `name @ URL` reference, which is neither resolved nor reported: the reference is recorded by its URL origin, so a variable in the user information, path or query is dropped with them, one in the host is kept literally, and a URL without `//` is kept as written;
  - a `${NAME}` variable inside an option's value, such as `--index-url https://${TOKEN}@host/simple`. pip expands variables before it splits a line, so a value containing spaces could add options, including an include;
  - index and source choices (`--index-url`, `--extra-index-url`, `--find-links`, `[[tool.uv.index]]`, Poetry primary or supplemental sources, and `.npmrc`); those packages are recorded as PyPI or npm packages, with the origin a lockfile record gives;
  - a PyPI range that an exact pin of the same package in another root file satisfies: the pin is taken as its resolution, as compiled pins resolve the ranges of `pyproject.toml`, even when that file is not the one installed;
  - dependencies declared only in `setup.py` or `setup.cfg`, or declared dynamic. A line that installs the project itself (`.`, `./`, `.[extras]`, `file:.` or `-e .`) is taken as covered by its `pyproject.toml`, and pip resolves such a path from the directory it runs in, which the collector takes to be the project root;
  - a `# syntax=` directive that selects another Dockerfile frontend;
  - in Compose files, anything but service images, inline Dockerfiles and top-level models, such as provider services; a file reached through `include`, `extends`, a `build` context or a `COMPOSE_FILE` in `.env` is a coverage gap, and so is a build that names contexts (`additional_contexts`, or `x-bake` `contexts` for `docker buildx bake`), which BuildKit uses in place of the image a `FROM` line names, but a `COMPOSE_FILE` set in the environment Compose runs in is not seen, nor are `docker buildx bake` files such as `docker-bake.hcl`;
  - manifests and lockfiles the collector does not read: requirements files in subdirectories, pip-tools `*.in` files, conda `environment.yml` and `[tool.hatch.envs]`; `Pipfile.lock`, `pdm.lock`, `bun.lock` and `bun.lockb` give each package they may resolve a low `lockfile_unread` finding, not a coverage gap (the **Lockfiles** item lists the lockfiles read);
  - Kubernetes manifests, Helm charts and `.devcontainer` configuration.
- **A2A values without a binding key.** A2A records export URLs only as origins: a network-path URL (`//host/...`), or a bare `host:port` address with a dotted, `localhost` or bracketed-IP host, as `//host:port`, and other scheme-less URLs, such as `svc:50051` or `host/path`, as `[redacted]`. The OAuth and OpenID Connect scopes that a card or its skills require are exported in clear. Requirement values of other scheme types, and of schemes the card does not declare, are not exported; the unkeyed structure digest covers them, on the card and on each skill, so changing one raises a medium alert, but anyone holding the BOM can confirm a guess of them, including a credential pasted there by mistake.
  - Without `NEXUS_SYMBIOTE_SOURCE_BINDING_KEY`, the following changes are detected only when they change a URL's shape (path depth, or whether a query, fragment or user information is present) or add or remove a top-level field of the card or client entry; fields inside skills, interfaces and security schemes are not covered, except the requirement lists, scheme types (for A2A 1.0, the scheme member) and URL fields (any field whose name ends in `url` or `uri`), where adding, removing or re-hosting one raises a medium alert:
    - a path or query change on the same host for a card's `url`, a `supportedInterfaces` or `additionalInterfaces` URL, a security scheme URL such as `tokenUrl`, or a client's `agentCardUrl` (a swap between `/.well-known/agent.json` and `/.well-known/agent-card.json` is detected);
    - any change to a URL whose origin cannot be exported, such as one without a host or with an invalid port, which is exported as `[redacted]`;
    - a changed A2A 1.0 interface `tenant`;
    - a changed scope that was redacted because it held user information, a query, a fragment, a credential assignment or a known token format;
    - values the inventory neither exports nor digests: security scheme fields other than types and URLs (such as an authorization code flow's `pkceRequired`, an API key's `name` and location, or an HTTP scheme's `scheme` and `bearerFormat`), `preferredTransport`, `protocolBinding`, `protocolVersion`, interface transports, descriptions, skill descriptions, tags, examples and input or output modes, and the id of a skill that has a name.
  - Records with an unbound URL, a tenant or a redacted scope carry a low `completeness` risk that names the key; it does not list the values the inventory neither exports nor digests. It is a risk, not a coverage gap, so gates on coverage do not fail on it, and the default risk gate, which fails only on critical findings, passes it; a risk gate set to fail on low severity fails on it.
  - A token endpoint or interface moved to another host raises at most a medium `properties changed` alert. It raises none when other URLs of that kind in the card already use the new host and still use the old one, or when the URL is exported as `[redacted]`. Supported interfaces are compared in order, and for an A2A 1.0 card without `url`, a change of the first entry's origin raises a high `endpoint_url changed` alert.
  - Scopes are read from the `security` and `securityRequirements` lists of the card and of its skills, not from `securitySchemes` flows. The specifications do not say how a skill's requirements combine with the card's, so skill requirements can make `authentication_required` false (a skill alternative that is empty or names an undeclared or untyped scheme) but never true: a card whose only requirements are on its skills is recorded as declaring none. A card that declares requirements in another form, or names a scheme that states no type or one the collector does not recognise, such as `none` (for A2A 1.0, no known scheme member), is recorded as declaring no authentication requirement. A legacy `authentication` object counts only for a card without `securitySchemes`, `securityRequirements` or `supportedInterfaces`, and not when it names only `none`, `public` or `anonymous`.
  - Cards are read in any `.well-known` directory and at `agent.json`, `agent-card.json` and `a2a/agent.json` in the project root, where they must carry an A2A field. A card built in Python code is a coverage gap. Card signatures are recorded by count, algorithm and key id, and are not verified.
  - Only the card's `url` and its first `supportedInterfaces` entry get the HTTPS check. A gRPC address in the `host:port` form that A2A 1.0 prescribes fails that check, because it does not show TLS.
  - A URL with a backslash before `@`, such as `https://evil.example\@good.example/`, is exported as `https://good.example` although WHATWG parsers connect to `evil.example`; its user-information shape raises only a medium alert.
  - The structure digests are unkeyed, so anyone holding the BOM can confirm guesses of field names, security scheme names, URL path depth and whether user information or a query is present.
- **RAG source values without a binding key.** RAG records export source URIs, and URLs in other fields such as `vector_store`, `embeddings`, a `sanitization` or `content_filter` value that is not a boolean, and the fields beside the `sources` list, as origins and check each for encrypted transport (a file with more than 1,000 such URLs is a collection failure); connection strings, `user:secret@host` forms and token-shaped values only as redaction markers; and inline documents only by count and digest. The structure digest covers field names, exported values, flags and URL shapes; other text and numbers, such as a control object's `mode` or a control written as `"strict"`, enter it only as their type. Without `NEXUS_SYMBIOTE_SOURCE_BINDING_KEY`, a same-host path or query change that keeps the path depth, and changed values that the record does not export, pass `diff --fail-on-alert`; a low `completeness` risk names the key. Configuration files are matched by name at any depth, another spelling of a name is a collection failure, and Python imports of vector-store libraries are an informational heuristic that skips files it cannot read or parse, within the source budget described under "Source collection is bounded by size".
- **ShadowScan producer verification is opt-in and not recorded.** Unless an operator signature policy names the discovery report, `--require-discovery-signature` is passed, or an honored project policy sets `validate.require_discovery_signature`, `validate` and `risk` accept unsigned ShadowScan evidence, and say so. The result of the check is not written into the BOM, so `validate` or `risk` without `--project` cannot enforce it, and a project-policy setting can be removed by the change it gates and is ignored under `--no-project-policy`. `verify-discovery --bundle` checks only a BOM written by `import-shadowscan`; for a merged `scan` BOM, use the signature policy with `--project`. A passing check authenticates the report's producer only. It does not bind the report to this repository, commit or time: anyone who can write to the checkout can substitute an older report, or another repository's report signed by the same identity, and regenerate the BOM from it. Give each repository's discovery workflow its own signer identity.
- **ShadowScan reruns need keyed credential identities.** When a report records `collection_scope.credential_identity_scope` as `run`, ShadowScan derived each redacted credential finding's id from a random per-run key. Those findings get new ids on every run, and `diff` reports them as removed and added components. Set `SHADOWSCAN_IDENTITY_KEY` for every ShadowScan run before you compare reruns.
- **Resource use on hostile input.** The [collection limits](docs/collection-limits.md) bound how much a scan reads, but some parsers can still spend minutes on crafted input within them. Export validation grows linearly with the inventory, but an SPDX export, which is validated against the official schema, takes about 50 to 120 milliseconds per component. MCP configuration files of under 2 MiB in all can declare 100,000 tools (one file holds at most 5,000), which keeps `scan -f spdx` running for hours. The scan does not pass in that time, but it can hold a CI job until the job times out, so set a timeout such as `timeout-minutes` in GitHub Actions. `validate --project` computes each artifact digest once per run, inspects and verifies each model weights file and each artifact the signer policy names for one component only (another model component naming it fails), and charges every artifact read, including model inspection and signature bundles, plus a fixed amount per signature verification, to a budget of six times the `model-total-bytes` collection limit (1.5 TiB by default), so an inventory that names one file many times cannot multiply the work beyond that budget; anything beyond the budget is reported as unknown. The weight files a model binds, such as ONNX external data, SavedModel variables and shard indexes, are read once per run within the model check's own budget of what one scan may read (the `model-total-bytes` limit, and twice the `entries` limit in weight-file bindings), and each signer policy entry is verified at most once per run.
- **Malformed input stops some exports with a traceback.** JSON-escaped lone surrogates (such as `\ud800`) in A2A agent cards or `package.json` make CycloneDX, SPDX and SARIF export exit 1 with a Python traceback (for an A2A card only when the value is in a field the record carries, such as the card's or a skill's name; a value in a requirement list or in the name of a skill with requirements is instead a scan failure, as is any such value when collected with `NEXUS_SYMBIOTE_SOURCE_BINDING_KEY`, and one in a field the record does not carry, such as `description`, exports cleanly), and the native JSON written for such input is refused by the other commands. This fails closed. Such a value in a field that a RAG record carries is a scan failure. An MCP tool definition deeper than 64 levels or larger than 20,000 nodes is a scan failure that names the limit.
- **GitHub Action.** On `pull_request`, GitHub runs the workflow file of the pull request's merge commit, so a pull request can change the Action's inputs, switch a gate off or delete the step, and its run passes. The Action prints every gate an input switches off as a warning and reports each gate in its `gates` and `result` outputs, but it cannot tell which workflow file a reviewer approved: protect the gate with a workflow that an organization ruleset requires, or with a `pull_request_target` job, as the README shows. An earlier step in the same job that runs untrusted code can change the runner's Python or rewrite files under `RUNNER_TEMP` before the Action reads them, so write the signer policy and the reviewed baseline from a trusted source and run untrusted build or test steps in a separate job. A SARIF upload replaces an earlier one for the same commit and `sarif-category`, and two steps in one workflow run need different `artifact-name` values.
- **Sigstore trust root.** Offline signature verification by the CLI uses the trusted root that sigstore-python caches in your user cache directory: `$XDG_CACHE_HOME/sigstore-python` whenever `XDG_CACHE_HOME` is set, on Linux and, with the pinned platformdirs, also on macOS; otherwise `~/.cache/sigstore-python` on Linux or `~/Library/Caches/sigstore-python` on macOS. Offline, sigstore-python reads that file without verifying it, so anyone who can write there chooses which certificate authorities and transparency logs are accepted. The GitHub Action gives its scans an empty private cache, so it always uses the root embedded in its hash-locked `sigstore` package. That root ages: a bundle that relies on a key Sigstore introduced after that release fails verification until you update the Action pin. On shared or persistent machines, such as self-hosted runners, run the CLI with `XDG_CACHE_HOME` set to an empty directory you own, on Linux and macOS alike; on macOS, setting `HOME` alone is not enough when `XDG_CACHE_HOME` is set.
