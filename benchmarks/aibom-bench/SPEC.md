# AIBOM-Bench specification

Version 1.0.0. This document defines what the benchmark measures, how each criterion is
scored, and what a score does and does not mean. The code is the definition where the two
differ: weights live in `aibom_bench/scoring.py` and the corpus in `aibom_bench/corpus.py`.

## What an AI-BOM tool is for

An AI bill of materials answers four questions about an AI system, and a reader acts on
the answers: what is in it, where did each part come from, what changed since it was last
approved, and what can each part do. The benchmark scores a tool on how well its output
supports those answers for four kinds of component:

| Pillar | Examples in the corpus |
| --- | --- |
| Models | Weight files (GGUF, SafeTensors, ONNX, PyTorch pickle), LoRA adapters, Hugging Face references, hosted API models, models named in Modelfiles, notebooks, Dockerfiles, Kubernetes arguments and configuration |
| Data | Training and evaluation sets, dataset cards, DVC pointers, fine-tuning uploads, vector stores, agent memory, knowledge sources |
| Tools | AI frameworks and SDKs in lockfiles, function tools defined in code, function-calling schemas, MCP tools |
| Agent components | MCP servers in six client formats, first-party MCP server source, skills, instruction files, prompts, subagents, slash commands, hooks, permissions, plugins, A2A cards, framework agents, guardrails |

A fifth group, infrastructure, covers the container images, endpoints and CI workflows the
components run on.

Three positions shape the weights:

1. **An inventory that misses a component cannot protect it.** Discovery carries the most
   weight, and agent components carry the most weight within it, because that is where
   the tools differ most and where existing software BOMs record nothing.
2. **The scanner reads hostile input.** A repository under review is attacker-controlled.
   A tool that launches a declared MCP server, deserializes a pickle, follows a symlink out
   of the project or prints a committed secret into the BOM has turned a review step into
   an attack path. Scanner safety is scored as heavily as risk analysis.
3. **A claim is not a measurement.** A capability earns full credit only when the harness
   or the assessor exercised it. A capability known only from documentation earns half.

## Method

Each tool is installed at a pinned version and run by one harness
(`aibom_bench/runner.py`) with the same wrapper:

- a new network namespace with only loopback, so no connection can leave the host;
- an empty environment with a private `HOME`, no credentials, `NO_COLOR=1` and
  `SOURCE_DATE_EPOCH` set;
- a working directory outside the project.

A tool runs against eleven variants of the corpus, always at the same path:

| Variant | Purpose |
| --- | --- |
| `base` | Discovery, fidelity, standards, risks, secret disclosure |
| `repeat` | The base corpus again, under `strace`, for determinism and attempted connections |
| `drift` | The base corpus with ten planted changes |
| `hostile:<case>` × 8 | One hostile-input case added to the base corpus |

Every output format a tool can write is collected. Records are extracted from those files
by one extractor (`aibom_bench/extract.py`) that reads CycloneDX, SPDX and SARIF by their
structure and any other JSON generically. No tool has a hand-written parser.

## The corpus

`acme-support-copilot` is one synthetic agentic application: a retrieval API, a refund
agent, two first-party MCP servers, training and evaluation code, deployment files and the
coding-agent configuration a team would commit. It is generated by `bench.py build`, not
committed, so this repository holds no pickle that runs a command, no secret-shaped string
and no invisible character.

| Label | Count | Meaning |
| --- | ---: | --- |
| Components | 91 | 18 models, 11 data, 18 tools, 36 agent components, 8 infrastructure |
| Facts | 194 | Version, supplier, digest, location, licence and domain facts a record should carry |
| Relationships | 7 | Edges such as agent uses tool, adapter derived from model, model trained on dataset |
| Decoys | 8 | Things that look like components and are not |
| Planted risks | 20 | One per risk class instance; one needs an online advisory lookup and is excluded offline |
| Clean controls | 6 | Benign counterparts a risk engine must not flag |
| Planted changes | 10 | Differences between `base` and `drift` |
| Execution canaries | 7 | A marker file appears if the scanner executed project content |
| Leak tokens | 7 | Four synthetic secrets and three out-of-tree markers |
| Hostile cases | 8 | See [8.5](#8-scanner-safety-12-points) |

Each component has **keys**, the distinctive strings that identify it, and a **kind**. Run
`python benchmarks/aibom-bench/bench.py build DIR` to read the corpus and
`DIR/ground-truth.json`.

Difficulty is deliberate. Some components sit where every tool looks: a root `.mcp.json`,
a `requirements.txt`. Others need format knowledge (JSONC, TOML, a GGUF header) or code
analysis (a model named in a Python call, a tool registered by a decorator). Some are
named only in configuration or an environment template. No tool is expected to find
everything, and a top score well below 100 is the intended result.

## How each measured criterion is computed

### 1 Discovery (30 points)

A component is credited from the tool's machine-readable output:

- **1.0, classified.** A record contains one of the component's keys and the record's own
  type information matches the component's kind. Type information is the CycloneDX `type`,
  `bom-ref`, `group` and property names; the SPDX element type and primary purpose; or, in
  other JSON, the values of type-like fields and the name of the list holding the record.
  The accepted vocabulary per kind is `KIND_PATTERNS` in `scoring.py` and is generous: an
  MCP server may be typed `mcp`, `server` or `service`.
- **0.5, present.** A record contains a key and is not a plain file entry, but its type
  does not match. The tool noticed the component and did not say what it is.
- **0.** No record, or only a file listing. Listing a model as a file is not inventory.

A pillar's score is the mean credit over its components.

### 2 Precision (4 points)

A decoy is reported when a non-file record contains its key and is typed as the kind the
decoy imitates. The score is one minus the share of decoys reported, and zero for a tool
that found under five percent of the real components, since such a tool has nothing to be
precise about.

The decoys are: a model ID in a commented-out line; ORM classes in a `models` directory;
model names in a blog post; a text file named `.gguf`; a YAML key `model:` naming a
printer; an MCP configuration inside `node_modules`; an MCP server in a commented-out
JSONC line; and a staffing table named `SKILL.md`.

### 3 Record fidelity (14 points)

For each detected component, the benchmark looks for expected facts in the text of every
record that matched it:

| Criterion | Fact classes | Examples |
| --- | --- | --- |
| 3.1 | Version, supplier | `2025.8.21`, a 40-character model revision, `meta-llama` |
| 3.2 | Digest | SHA-256, SHA-512, SHA-1 or MD5 of the file's bytes |
| 3.3 | Location | The repository path the component was found in |
| 3.4 | Domain, licence | Base model, quantization, transport, launcher, credential reference, `cc-by-nc-4.0` |

The score is the share of expected facts found among detected components, multiplied by
`min(1, n / 8)` where `n` is the number of detected components that carry such a fact. The
multiplier stops a tool earning full depth credit from one or two records.

**3.5 Relationships** is the share of the seven edges for which both ends were detected
and either the documents link their references (CycloneDX `dependencies`, SPDX
relationships) or one end's record names the other.

### 4 Standards (10 points)

- **4.1, 4.2, 4.5.** Each emitted document is validated against the upstream JSON schema
  for the version it declares: CycloneDX 1.4 to 1.7, SPDX 2.3 or 3.0.1, SARIF 2.1.0.
  Valid scores 1, emitted but invalid 0.5, not emitted 0. Valid SPDX 2.x scores 0.5
  because the AI and Dataset profiles exist only in SPDX 3. Only structure is checked.
- **4.3.** `0.5 ×` the share of detected models typed `machine-learning-model`, plus
  `0.3 ×` the share of detected datasets typed `data`, plus `0.2` if any component has a
  model card.
- **4.4.** `0.7 ×` the share of detected framework packages carrying a `pkg:pypi` or
  `pkg:npm` URL, plus `0.3` if any record carries a `pkg:huggingface` URL.

### 5 BOM integrity (10 points)

- **5.1.** Compare each machine-readable output of `base` and `repeat`. All byte-identical
  scores 1. All identical after removing time, serial and identifier fields scores 0.6.
  Otherwise 0.
- **5.3.** In the `hostile:malformed` run, a machine-readable output that names a file the
  tool could not parse scores 1; naming it only on the console scores 0.5.

### 6 Risk analysis (12 points)

A planted risk is caught when a finding names the affected component and uses the
vocabulary of the risk class (`SIGNALS` in `corpus.py`). Findings are SARIF results,
CycloneDX vulnerabilities, JSON objects that carry both a severity and a message, and
console lines. Automatic matching over free text is fallible in both directions, so every
verdict is reviewed and corrections are recorded with a reason under `adjudication` in
`assessments/<tool>.json`. The rule applied: a risk counts when the tool states it as a
finding, a warning or an explicit risk flag on the affected component; a neutral attribute
the reader must interpret, such as the bare string `latest`, does not.

**6.1** is the share of the 19 offline risks caught. **6.2** is one minus the share of the
six clean controls flagged, and zero for a tool that caught nothing.

The risk classes: code-executing pickle; unpinned `npx`, `uvx`, model revision and CI
action; credentials in an MCP header and an environment file; a poisoned MCP tool
description; hidden instructions in a skill and in a rule file; a skill script that pipes a
download to a shell; a shell-wildcard permission allowlist; a shell tool; a typosquatted
dependency; plain-HTTP MCP transport; an instruction import that leaves the repository; an
inline-shell MCP launch command; an agent that combines untrusted input, private data and
an outbound channel; and personal data under a non-commercial licence. The twentieth, a
bridge package at a version with a published advisory, needs an online lookup.

### 7 Change detection (8 points)

- **7.1.** For each planted change, compare the records that contain the changed
  component's key in `base` and `drift`. A modification is visible when those records
  differ and did not differ between `base` and `repeat`; an addition or removal when the
  records appear or disappear. This measures whether the BOM is sensitive to the change at
  all, independent of any diff tool.
- **7.2.** If the tool has a drift command, it is run on its own two outputs. The score is
  the share of changes whose key appears in the report.

The changes: a tool description gains an instruction; an MCP server changes version and
widens its filesystem root; a server is added; a server is removed; model weights change
under the same name; a skill's allowed tools widen; a pinned model revision changes;
permissions switch to bypass mode; a system prompt's rule is reversed; a row is appended
to the training set.

### 8 Scanner safety (12 points)

- **8.1.** Seven canaries: a declared MCP launch command, a pickle, a hook, a skill script,
  an npm lifecycle script, `setup.py` and a Python package's import. Any marker present
  after the `base`, `repeat` or `drift` scan scores 0.
- **8.2.** Half for not emitting the content, digest or inventory of an out-of-tree file
  reached through an instruction import, half for the same through symbolic links.
- **8.3.** One minus the share of the four synthetic secrets that appear verbatim in any
  output, console included.
- **8.4.** Half if the raw terminal escape sequence planted in a component name is absent
  from console, text and Markdown output; half if the raw HTML is absent from HTML and
  Markdown output.
- **8.5.** The share of hostile cases passed. A case passes when the scan finishes inside
  180 seconds and retains at least 90 percent of the component credit it earned on `base`.
  The cases: symlinks out of the project; symlink loops; configuration nested 200,000
  levels; truncated and invalid files; model headers claiming 2^62 entries; named pipes;
  hostile names; and 30,000 extra files with a 1 GiB sparse model.
- **8.6.** Half for producing an inventory with no network, half for attempting no
  connection to a non-loopback address.

## Assessed criteria

Seven criteria cannot be computed from scan output. Each is a level of 0, 0.5 or 1 with a
written evidence line and an evidence tier in `assessments/<tool>.json`:

| Tier | Meaning | Credit |
| --- | --- | --- |
| V | The assessor ran the feature and saw it work | full |
| S | Read in the tool's source | full |
| D | Stated in help text or documentation only | half |
| N | Not assessed or absent | none |

| Criterion | Level 1 | Level 0.5 |
| --- | --- | --- |
| 4.6 | A command reports coverage of a named minimum-element set or maps findings to a published framework | Framework tags on findings only |
| 5.2 | Signs or attests the BOM and verifies an attestation against a trusted key | Signs or attests without a verification path, or for another artifact type only |
| 5.4 | Output states which collectors ran and marks the inventory complete or partial | Console-only statement |
| 5.5 | Each record states how it was established, such as declared versus observed, or a confidence | Present on some records |
| 6.3 | Looks up advisories for exact package identities and exports VEX | One of the two |
| 7.3 | Documented exit codes for a policy or severity gate, exercised | Exit code on findings only |
| 7.4 | Compares the inventory with observed behaviour: a live MCP tool listing or runtime traces | Live discovery without comparison |

## Grades

Fixed before any tool was run:

| Total | Grade |
| ---: | :---: |
| 85 to 100 | A |
| 70 to 84 | B |
| 55 to 69 | C |
| 40 to 54 | D |
| 25 to 39 | E |
| under 25 | F |

A grade describes fitness as a complete AI-BOM tool across all four pillars. A
single-purpose tool that does one job well will grade low; read its group scores.

## Threats to validity

- **Conflict of interest.** The benchmark was written in the repository of one of the
  graded tools. The mitigations are that the corpus was designed from the component
  taxonomy and public file formats before any tool was run, the same harness and extractor
  run every tool, the ground truth and every output are reproducible from this tree, and
  the adjudication of every risk verdict is recorded. They reduce the bias and do not
  remove it. An independent party should rerun the benchmark before the ranking is cited.
- **One corpus.** One synthetic project cannot represent production systems. A tool can be
  tuned to it. Scores say how tools behave on these files, not how they rank in general.
- **Offline only.** Hugging Face metadata, advisory databases and registries were not
  reachable. Tools whose value is online enrichment are under-measured, and a tool that
  takes a model ID in place of a directory cannot be measured at all.
- **Key matching.** Detection relies on distinctive strings and a type vocabulary. A tool
  that reports a component under a name the keys do not anticipate is under-credited; one
  that echoes file contents is over-credited. Per-component verdicts are in `results.json`
  for audit.
- **Default configuration.** Each tool ran with the flags its help text documents for a
  directory scan and all its output formats. Optional LLM enrichment, cloud scanning and
  live modes were not enabled.
- **Uneven verification of assessed criteria.** Signing and verification were run by hand
  for Nexus SymBiote only; for agent-bom and cdxgen they were read from help text and earn
  half credit (1.5 points each). Running them would likely close that gap.
- **Three scores are floors.** Cisco AI BOM ran without the LLM it requires, Snyk Agent Scan
  without its hosted analysis, and the OWASP AIBOM Generator without Hugging Face. See the
  results page.
- **No statistical claim.** There are no confidence intervals. A difference of a few
  points between two tools is not a finding.
