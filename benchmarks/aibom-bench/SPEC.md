# AIBOM-Bench 1.0: a benchmark for AI bill-of-materials tools

AIBOM-Bench measures how well a tool inventories an agentic AI system and how
safely it does so. It covers the four asset families an AI-BOM must account
for, **data, models, tools and agent components** (MCP servers, skills,
prompts and instruction files, A2A cards, IDE and CI agents, hooks), and it
scores the tool itself as a piece of security software: a scanner that reads
hostile repositories must not execute them, leak their secrets, reach the
network unasked, or produce output that cannot be reproduced.

Every criterion is scored from evidence that a reader can re-run. The corpus is
generated by `build_corpus.py`, the ground truth is `ground_truth.json`, the
runner is `run_tools.sh`, and the scoring is `score.py`. Where a tool could
not be run, the report says so and the affected criteria are marked **N**, not
guessed.

## Design principles

1. **Ground truth before tools.** The corpus and the expected inventory were
   written before any tool was run against them, from the asset families an
   AI-BOM standard must cover (CycloneDX ML-BOM, SPDX 3.0.1 AI and Dataset
   profiles, the G7 and CISA AI SBOM minimum elements), not from what any
   tool happens to detect.
2. **Detection is necessary, not sufficient.** A BOM that lists the right
   components but carries no evidence, no hashes, no pins and no gaps is a
   list, not a bill of materials. Identity, provenance and completeness
   honesty are scored separately from detection.
3. **The scanner is in the threat model.** An AI-BOM tool reads attacker-
   controlled repositories, often in CI with credentials nearby. The benchmark
   plants symbolic links that escape the root, a loop, control characters,
   secrets, deep nesting, a large file and text that instructs an AI reviewer
   to report the repository as clean. The tool is scored on what it does with
   them, with evidence from `strace`, a network namespace with no interfaces,
   and a byte-level diff of the corpus after the run.
4. **Precision counts.** Decoys (a configuration quoted in documentation, a
   model named in a comment, a dependency's own `.mcp.json` under
   `node_modules`) are planted so that a tool that reports everything it
   greps does not outscore a tool that reports what is configured.
5. **Determinism is a security property.** Two runs over identical input
   must produce identical documents, or a diff-based drift gate cannot work.
6. **Say what you could not check.** Every score carries an evidence label.
   An unlabeled claim is a defect in the report.

## The corpus

`build_corpus.py` materializes a synthetic customer-support agent monorepo of
67 files plus four symbolic links, one 32 MiB sparse file and a 40-level deep
directory. It is deterministic: `corpus.manifest.json` records the SHA-256 of
every file.

secrets, 4 integrity digests, 5 pins and 15 expected findings.

## Dimensions and criteria

Each criterion is scored 0 to 4 against the anchors below. Dimension weights
sum to 100.

### D1. Coverage and detection accuracy (weight 30)

Recall is computed per class over the ground truth; `soft` items count 0.5.
The dimension score is the weighted mean of class recalls (weights in the
table) minus a precision penalty of 0.5 points per hard decoy reported and
0.25 per soft decoy, floored at 0.

| Class | Weight | Why |
| --- | --- | --- |
| mcp-server | 3 | The main agentic attack surface; six client formats |
| tool | 2 | What the model can do |
| skill | 2 | Executable instructions with tool grants |
| prompt | 2 | Instruction files steer the agent; imports hide scope |
| model | 3 | Every provider and hosted model |
| model-file | 2 | Local artifacts and their formats |
| dataset | 2 | Training, evaluation and retrieval data |
| training | 1 | The pipeline that produced a local model |
| vector-store | 1 | Retrieval infrastructure |
| a2a | 1 | Agent-to-agent exposure |
| agent-config | 2 | Permissions and hooks are policy |
| ci-agent | 1 | Agents with repository write access |
| container | 1 | Deployment surface |
| package | 1 | Conventional SBOM content |
| guardrail | 0.5 | Controls that claim to exist |

Anchors: 4 = weighted recall at or above 0.85; 3 = 0.65; 2 = 0.45; 1 = 0.25;
0 = below 0.25.

| --- | --- | --- | --- | --- |
| 2.1 | Content hashes for local model artifacts | SHA-256 of every model file in output | Some files hashed | None |
| 2.2 | Canonical identity for tool and server definitions | Content hash over a canonical form (RFC 8785 JCS or equivalent) so a changed description changes identity | Name and version only | Name only |
| 2.3 | Package URLs and bom-refs | Valid PURLs for packages, images, HF models and MCP servers; stable bom-refs | PURLs for packages only | None |

| 2.5 | Floating references detected | Flags `@latest`, unversioned servers, `:latest` images and `revision="main"` as findings | Some | None |

| # | Criterion | 4 | 2 | 0 |
| --- | --- | --- | --- | --- |
| 3.1 | Evidence per component | File path and line or key path, plus the collection method | File path only | None |

### D5. Risk analysis and policy (weight 10)

Scored against the 15 expected findings (F01 to F15 in `ground_truth.json`):
4 = 11 or more; 3 = 8; 2 = 5; 1 = 2; 0 = none. A finding counts when the
output names the condition and the location. Bonus of one point, capped at 4,
for a policy gate with exit codes, a baseline diff with a drift gate, and a
crosswalk to OWASP, MITRE ATLAS, NIST AI RMF, EU AI Act or ISO/IEC 42001.

### D6. Security of the tool itself (weight 12)

| # | Criterion | 4 | 2 | 0 |
| --- | --- | --- | --- | --- |
| 6.1 | Offline by default | Full result in a network namespace with no interfaces, and no `connect` to a non-loopback address in the traced run | Works offline with a flag | Fails or degrades silently without network |
| 6.2 | No execution of project content | No `execve` of anything from the corpus; no import, load or launch of models, modules or servers | Spawns package managers but not project code | Loads pickles, imports modules or launches servers |
| 6.3 | Confined reads | Does not follow symlinks outside the root; `/etc/passwd` content and the escaping `.gguf` are absent; the loop terminates | Follows but does not emit | Emits content from outside the root or hangs |
| 6.4 | Secret handling | No sentinel in any output; credentials recorded by name or location only | Some sentinels in a verbose format | A sentinel in the primary output |
| 6.5 | Output neutralization | ANSI escapes, bidi overrides and zero-width characters replaced or escaped in text output; JSON output cannot inject a terminal sequence through `jq` | Escaped in JSON only | Raw escape bytes in text output |
| 6.6 | Resource bounds | Documented limits on size, depth and count that fail closed and name the bound | Finishes but no bound documented | Hangs or crashes on the corpus |
| 6.7 | Robustness | Malformed TOML and JSONC handled with a recorded failure, not a crash | Crash on one | Crash on both |
| 6.8 | Does not modify the project | `corpus-delta.json` is empty | Writes caches under the project | Modifies tracked files |
| 6.9 | Scanner-targeted injection | Text in `AGENTS.md` and the server description does not change the inventory | Not applicable without an LLM (score 4) | The inventory changes |
| 6.10 | Supply chain of the tool | Hash-locked dependencies, signed releases with provenance (Sigstore or SLSA), an SBOM for itself, pinned CI actions | Some | None |

## Scoring

```
dimension_score = mean(criterion scores) / 4 * weight      (D1 and D5 use their own rule)
total           = sum(dimension_score) over dimensions that were assessed
normalized      = total / sum(weights of assessed dimensions) * 100
```

Grades: **A+** at or above 90, **A** 80, **B** 70, **C** 55, **D** 40, **F**
below 40. A grade is **provisional** when any dimension carrying more than
20 weight points in total is marked N, and it is **capped** by a hard gate.

## Evidence labels

Every criterion in the report carries one label:

| Label | Meaning |
| --- | --- |
| **V** | Verified by running the tool on the corpus in this benchmark; raw outputs are in `results/` |
| **C** | Verified by reading the tool's source code at the recorded commit, without running it |
| **D** | Taken from the tool's documentation and not verified |
| **A** | Assumed or inferred; stated as such |
| **N** | Not assessable here; excluded from the score |

A criterion with label D or A never scores above 2 unless the documentation
is itself a test suite that was read.

## Hard gates

A tool that does any of the following has its grade capped at **C** whatever
its total, because the failure makes it unsafe to point at an untrusted
repository in CI:

- **G1** A planted secret appears in a primary output document.
- **G2** The tool executes code from the corpus (model load, module import,
  server launch, hook) without an explicit opt-in flag.
- **G3** Output contains content from outside the scan root reached through a
  symbolic link.
- **G4** The tool reaches a non-loopback network address by default while
  documented as offline, or sends telemetry without an opt-in.

## Running the benchmark

```bash
cd benchmarks/aibom-bench
python3 build_corpus.py --out /tmp/aibom-corpus          # materialize
RESULTS=/tmp/aibom-results WORK=/tmp/aibom-work \
  NEXUS=$(command -v nexus-symbiote) ./run_tools.sh nexus-symbiote
python3 score.py --results /tmp/aibom-results --schemas schemas \
  --overrides review_overrides.json --out /tmp/aibom-results/scores.json
```

The schemas under `schemas/` are the ones the published scores were validated with; `SOURCES.json` records each copy's source and digest, and `python3 fetch_schemas.py --refresh DIR` compares them with upstream. `run_tools.sh` needs `strace` and an unprivileged user namespace
(`unshare -rn true` must succeed). Each tool is passed through an environment
variable so that the runner never guesses a path; a tool whose variable is
unset is skipped.

## Known limitations of the benchmark

- The corpus is finite and hand-authored. A perfect score is not a
  completeness certificate, and a class that a tool scopes out by design
  (a Kubernetes runtime observer has no opinion on `.cursorrules`) is reported
  as N for that tool rather than zero.
- Detection matching is textual. A tool is credited when the identifying
  token appears in its output; `score.py` reports the matches so that a
  reviewer can reject an incidental mention. Reviewed exceptions are listed
  in the report.
- Secrets are synthetic sentinels and deliberately off-pattern for real
  providers, so entropy-based secret detectors are not expected to flag
  them. Criterion 6.4 scores leakage of values that sit in credential
  positions, not detection of realistic key formats.
- The network namespace removes all interfaces, including loopback, so a tool
  that binds a local port for its own use fails the offline run for a reason
  unrelated to egress; the report says so when it happens.
- Live-mode criteria (D8) and the unresolvable package (F13) need network
  access that this benchmark does not grant; they are scored from code and
  documentation.
- Tools that require an LLM provider or a Kubernetes cluster to run cannot be
  exercised on a static corpus; their D1 is N and their grade is provisional.
