## What this is

An AI bill of materials (AI-BOM) generator reads a project and writes an inventory of the AI system it holds: models, data, tools and the components of agents, such as MCP servers, skills and instruction files. This benchmark runs several generators on the same generated projects and compares what each writes with what is actually there.

It is a first-party benchmark. It lives in the repository of one of the tools it grades, and one author wrote the cases and their labels. The design compensates for that as far as a design can: every rule is applied to every tool by the same code, the raw commands and versions are recorded, the scorer is calibrated, and the corpus, rules, weights and grade bands were committed before any tool was run on the corpus (see [changing the benchmark](#changing-the-benchmark)). It does not replace an independent evaluation; the project's roadmap lists that separately.

Passing every case would not make a tool complete or safe. The corpus is finite and synthetic.

## Principles

1. **The standard document is what counts.** Discovery, attributes, relationships and conformance are read from the CycloneDX document, because that is what a consumer receives. What a tool knows but does not export is reported beside the score, not in it.
2. **No tool-specific scoring.** An adapter states a command line and an output path. It never edits an output. The scorer has no branch on a tool's name.
3. **Surfaces come from outside.** A surface is in the corpus when a published format or the documentation of at least one graded tool names it. Every case lists those sources. Surfaces that the host tool does not read are included on the same terms.
4. **Measured, not claimed.** A capability counts when a run shows it. A tool that cannot be run in the round has no score, with the reason stated.
5. **Isolated and repeatable.** Every run happens with no network, an empty home directory, a cleared environment and fixed paths.
6. **Differences, not vocabularies.** Risk detection is judged by comparing two cases that differ in one condition. No rule name or severity scale is mapped.
7. **Engagement before safety.** A tool is credited for surviving a hostile input only when it also reports the ordinary component beside it. Ignoring a surface is not safe handling of it.
8. **Calibrated.** A document built from the labels must score 100 and an empty one 0.

## Scope of a round

A round has one track, the **repository track**: the input is a directory, the tool runs offline, and the output is a CycloneDX JSON document.

Three things follow, and each excludes something real:

- Tools whose input is not a directory have no score: a model-registry identifier (OWASP AIBOM Generator) or a running cluster (k8s-aibom).
- Tools that need a network service to produce an inventory have no score: an LLM provider (Cisco AI BOM's `analyze`).
- Capabilities that need a network service are outside every score: vulnerability matching, registry and model-hub lookups, LLM classification or enrichment.

## The corpus

The corpus is generated by code (`bench/cases_*.py`) and never stored as fixture files. Generation is deterministic; one digest covers every byte it writes, and a test pins that digest. Credential-shaped canaries and files with invisible characters therefore exist only in a materialized corpus, not in this repository.

| Part | Count | Purpose |
| --- | ---: | --- |
| Discovery cases | 41 | 128 labelled components in five domains, with 241 attribute checks, 29 relationships and 7 decoys |
| Risk pairs | 14 | A clean and a risky twin that differ in one condition |
| Hostile cases | 15 | Projects built to make the scanner execute, escape, leak, hang or crash |
| Mutations | 14 | One supply-chain relevant change to a discovery case |

The [case catalog](#case-catalog) lists every case.

### Labels

A label names a component that is present in a case. It holds:

- **Tokens** that identify it, such as a server's configured name or a model identifier. Token groups are alternatives; all tokens of one group must occur.
- **Attributes** a reviewer needs: version, package URL, SHA-256 of the backing file, source location, license, the CycloneDX type where the standard defines one (`machine-learning-model`, `data`), and case-specific facts such as a launch command, an endpoint or a base model.

The five domains and their label counts are models (25), data (11), tools (14), agent components (45), and packages and platform (33).

A self-check (`python -m bench check`) fails if a token or attribute value does not occur in its case, if a relationship or decoy refers to a missing label, or if a mutation changes nothing.

### Controls

Every case also holds four files with no AI content: a Markdown note, a JSON settings file, a PNG image and a Python module. They show how a tool renders an arbitrary file. The binary control is an image because `.bin`, the first choice, is also a model-weight extension.

### Decoys

Seven cases contain text that looks like a component and is not one: a server in a documentation example, a model named in a comment or a log message, a dataset named in a docstring, a commented-out requirement, an undecorated function beside decorated tools, and a skill shown as an example. Each decoy is paired with a real component of the same surface in the same case.

### Risk pairs

Each pair is two cases with the same paths, where one file differs in one condition: a pickle that runs a command, a floating package reference, a plain-HTTP endpoint, a literal credential, a hidden instruction. The fixture text contains none of the words in `RISK_WORDS` (`bench/cases_risk.py`), so a tool that copies fixture text into its output cannot appear to have raised a signal.

### Hostile cases

Each case holds a hostile input and an ordinary component, the *survivor*. Canaries make misuse observable:

- **Execution**: commands in fixtures create a file in a directory that starts empty, or a file with a canary name in the project.
- **Escape**: files outside the scanned directory carry a marker and known digests.
- **Disclosure**: credential-shaped values are derived at materialization and searched for in every output and in the files the tool leaves in its home directory.
- **Control sequences**: names carry terminal escape sequences followed by markers.

No fixture is loaded, unpickled, rendered or launched by the benchmark itself.

### Mutations

Each mutation changes one thing a reviewer would want to know about: a server's version or endpoint, a byte of model weights, a skill's text or script, an instruction, a hook, a tool's description or schema, a dataset row, a package version, an agent card's endpoint, a system prompt.

## How tools are run

Each run materializes one case into a new directory and starts the tool inside new network and mount namespaces (`unshare --net --mount`):

| Path in the sandbox | Content |
| --- | --- |
| `/mnt/bench/case` | The project; the working directory. For the relocation run, `/mnt/bench/elsewhere/checkout/case` |
| `/mnt/bench/home` | An empty home directory. For the user-scope case, the project is the home directory |
| `/mnt/bench/out` | Where the tool writes its output |
| `/mnt/bench/canary` | An empty directory that fixtures try to write to |
| `/mnt/bench/outside` | Files that are not part of the project |

The environment is cleared and then set to `HOME`, the XDG directories, `PATH`, `LANG`, `LC_ALL`, `TZ=UTC`, `TERM=dumb`, `NO_COLOR=1`, `CI=true` and the variables an adapter lists. A run is stopped after 120 seconds, or when the tool's resident memory passes 3 GiB.

**Invocation policy.** Each tool gets its documented AI-BOM command with only the flags needed to choose the output file and format, to be quiet, to stay offline and to switch telemetry off. No flag that turns a gate on or off is passed; exit codes are recorded as they come. The exact commands are in `bench/tools.py` and are printed in every report.

**Formats.** CycloneDX JSON is requested for every case. SARIF and the tool's own JSON format, where it has them, are requested for the risk pairs and hostile cases; the tool's own JSON is also requested for discovery cases, for the diagnostic in the report.

**What is recorded.** Exit code, wall time, peak resident memory, whether the limit was hit, the output, the console streams, files created in the canary directory, every path the tool created, changed or removed in the project, and whether a canary credential appears in the files it left in its home directory.

Tool versions are pinned: Python tools by hash-locked requirements, cdxgen by a lockfile installed without package scripts, Go tools by module version (`tools/`).

## How output is read

An **element** is any object in a `components`, `services`, `workflows` or `tasks` list, or under a `component` key, anywhere in the document. Its text is every string and number it holds, lower-cased, without the elements nested inside it.

An element **names** a label when every token of one of the label's groups occurs in its text.

An element's **signature** is its kind, its `type`, its property names, and its property values that read as labels (short, no path separators, not digests or numbers). The signatures of elements that mention a control file are the tool's *generic* signatures: how it renders a file it knows nothing about.

A label is **found** when an element names it and that element's signature is not generic. Listing a model file the same way as a PNG is not discovery.

This matching is deliberately lenient about *where* a tool records a fact, because the standards do not yet fix a representation for MCP servers, skills or instruction files. It is strict about *whether* the fact is there.

## The nine pillars

Each pillar is a number from 0 to 1.

| Pillar | Weight | Definition |
| --- | ---: | --- |
| Discovery | 30 | For each domain, labels found divided by labels present; the pillar is the mean of the five domains, so a large domain does not dominate. The report gives counts and a 95% Wilson interval per domain |
| Precision | 8 | Decoys rejected divided by decoys. A decoy is rejected when no element names it **and** its paired real component was found |
| Attributes | 12 | Attribute checks that hold, divided by all attribute checks of all labels. For a found label the best matching element is used; for a label not found every check fails. The report also gives the share for found labels only |
| Relationships | 5 | Labelled relationships that the document expresses, divided by all. Two found components are related when one element names both, when one is nested in the other, when `dependencies` links them in either direction, or when one refers to the other's `bom-ref` |
| Conformance | 8 | Mean over discovery cases of a case value; a case with no found label has value 0. The case value is the mean of the checks that apply: strict validation against the official CycloneDX schema of the declared version (with `cyclonedx-python-lib`), the share of package URLs that are syntactically valid, unique `bom-ref` values, and the share of found models and datasets that carry the standard type |
| Risk signal | 12 | Mean credit over risk pairs. 1 when a machine-readable output of the risky twin holds a risk statement that the clean twin's does not: a SARIF result, a CycloneDX vulnerability or annotation, a property whose name matches the risk pattern in `bench/score.py`, or such a field in the tool's own JSON. 0.5 when only the console text contains more risk words or the exit code differs. 0 otherwise |
| Hostile input | 12 | Mean credit over hostile cases. A case earns the share of its checks that pass if the tool found a survivor, and 0 if it did not |
| Reproducibility | 5 | Mean over the twelve base cases of the mutations. An engaged case earns the mean of two comparisons, a repeat in place and a scan from another directory: 1 when the documents are equal after removing `serialNumber` and `metadata.timestamp`, 0.5 when they are equal only after also removing UUIDs, timestamps and list order, 0 otherwise |
| Change sensitivity | 8 | Mutations detected divided by mutations. A mutation is detected when the tool found the changed component in the base case, two scans of the unchanged base agree in the lenient comparison above, and the mutated project's document differs from the base |

Hostile checks:

| Check | Passes when |
| --- | --- |
| completes | The tool ended on its own within the limit, was not killed by a signal, and wrote a CycloneDX document that parses |
| no execution | The canary directory is empty and no file with a canary name appeared in the project |
| no escape | No output contains the marker or a digest of a file outside the project |
| no secret disclosure | No output, and no file the tool left in its home directory, contains a canary credential |
| no terminal escape | The console streams contain no escape byte in front of a marker |
| bounded memory | Peak resident memory stayed below 2 GiB |
| not steered | Every component found without the text addressed to scanners is also found with it |

## Composite score, grades and weight sensitivity

The composite is the weighted sum of the nine pillars, out of 100. Grades: A from 85, B from 70, C from 55, D from 40, F below 40.

The weights are a judgment: inventory first (55 of 100 for discovery, precision, attributes and relationships), then whether the document can be relied on. Every report therefore also ranks the tools with equal pillar weights, with the inventory pillars only, with the four assurance pillars doubled, and with each pillar left out in turn. A rank that holds across those is robust to the weights; one that does not is an artifact of them.

A specialist is graded on the whole surface. A tool that reads only model files can be excellent at that and still score low overall; the per-domain table is where its strength shows.

## Calibration and tests

Two built-in tools bound the scale and run with every scoring: the **oracle** writes a document from the labels and must score 100 on every pillar; the **null** tool writes a valid empty document and must score 0.

`tests/test_comparative_benchmark.py` checks the corpus against its labels and its pinned digest, the calibration, and that each rule rejects what it should: uniform file listing earns no discovery, a reported decoy is not rejected, each hostile check fails on its canary, console-only risk output earns half credit, and random identifiers cost strict reproducibility but not change detection.

## What the results do not show

Read these before quoting a number.

- **The corpus is synthetic and small.** 128 labels in 41 cases, written to be unambiguous. Real repositories are larger, messier and distributed differently across surfaces. The intervals in the report are wide; small differences between tools are not evidence.
- **One author, no blinding.** The labels were written by the author of the cases, with knowledge of what several tools read. No second labeller reviewed them.
- **First-party.** The benchmark is developed with one of the graded tools. The surface list was drawn from every tool's documentation and from published formats to counter that, and the host tool is shown losing wherever it loses, but selection effects cannot be excluded from the inside.
- **Token matching can over-credit.** A label is found when its tokens occur in a recognized element. A tool that records a name without understanding the component earns the discovery credit; attribute checks then separate shallow from deep records only where a label has attributes.
- **CycloneDX first.** A tool whose own format carries more than its CycloneDX export is scored on the export. The report shows the difference; the score does not include it.
- **Defaults, offline.** Every tool ran with its documented command and no tuning, without a network. A maintainer could likely configure a better result, and online features are absent by design.
- **The risk comparison is coarse.** It credits any new risk statement in the risky twin, whatever it says, and it reads only the channels listed above. It does not measure false alarms on clean projects.
- **Engagement gating has two edges.** It denies credit for safety by omission, and it also means a tool that is safe on a surface it does not inventory shows as "not engaged", not as safe.
- **One environment, one date.** Versions are those pinned on the day of the round, on one Linux machine. Tools change monthly.
- **Weights and bands are judgments.** They were fixed before the first run and are not derived from data.

No score here supports a statement about a tool's rank among all tools, or a percentile.

## Areas specified but not scored

These belong to an AI-BOM tool's value and are outside version 1.0. Each needs a per-tool probe that its maintainers would accept, or a network:

- Signing and attestation of the document, and verification that fails after tampering.
- Diff and gate commands, as distinct from a document that changes.
- VEX output, and vulnerability and advisory matching.
- Validity of SPDX 3.0.1 and SARIF 2.1.0 exports.
- Coverage of the G7 AI SBOM minimum elements.
- A model-registry track (input: a model identifier) and a cluster track (input: a running cluster).
- Runs with an LLM in the loop, including whether text in a repository can steer the inventory. Case `h11-steering-text` exists for that and passes trivially for deterministic tools.
- Performance on large repositories.

## Changing the benchmark

The corpus, the scoring rules, the weights and the grade bands were committed before any tool was run on the corpus. Tool adapters were developed against a separate smoke project that is not part of it. Every change after that commit is listed in [DEVIATIONS.md](DEVIATIONS.md) with its reason and its effect on every tool, and a change to a case or label changes the pinned corpus digest.

To add a tool, add an adapter to `bench/tools.py` with its pinned version and exact command, and nothing else. To dispute a label or a rule, open an issue with the case identifier; a correction is applied to every tool and recorded as a deviation.
