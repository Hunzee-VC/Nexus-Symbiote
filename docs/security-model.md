# Security model

Nexus SymBiote connects an agent's inventory to evidence and policy. Keep the following states separate:

| State | Meaning |
| --- | --- |
| Declared composition | A repository, supplier, or configuration says a component is used. |
| Observed composition | A named collector measured a component in a stated scope and time. |
| Approved configuration | An authorized approver accepted a specific configuration and capabilities. |
| Mediated execution | An enforcement adapter checked an actual action against its trusted policy and approval. |

A component's `assurance_level` describes its identity: `observed` when a collector computed it from bytes (a weight, instruction, skill or tool-descriptor digest), `declared` for a configuration, manifest, package pin or supplier statement. Each locally collected component also carries a `repository_presence` claim naming the collector that observed it.

Nexus-ShadowScan is the primary discovery source; importing its report into Nexus SymBiote preserves the distinction between a supplied claim and a new local measurement. A2A Agent Cards, IDE configuration, and extension manifests are declarations until their relevant identity and evidence are separately verified.

An inventory entry never grants permission by itself. A schema hash pins an interface; it does not constrain a backend's hidden side effects. A signed malicious artifact remains malicious. Runtime metadata emitted by the agent itself has a different trust basis from an independent observation.

Collectors must preserve coverage limitations, denied reads, unsupported inputs, exclusions, and failures. Some unsupported inputs are still skipped without a gap; the [known limitations](known-limitations.md) list them. Missing information means unknown, not verified absence. Secrets are references, not values. Avoid default capture of raw prompts, retrieved documents, tool arguments, or results. Tenant and deployment identifiers must remain part of approval and observation scope.

## Design principles

1. **Never runs what it inspects.** Collection is static. It does not execute project modules, model loaders, repository hooks or MCP launch commands.
2. **Offline by default, enforced at run time.** Every command runs under a tripwire that makes this package and its dependencies fail closed on name resolution, network connections and process creation unless you opt into live mode for one of three commands. It is not a sandbox; add an operating-system network boundary where one is required.
3. **Unknown is not safe.** Failed reads, skipped collectors and the unsupported declarations a collector recognizes are recorded as gaps, and default gates fail on them instead of passing silently. Surfaces the collectors do not support are not recorded at all; the [known limitations](known-limitations.md) list them.
4. **Claims are not evidence.** Declared, observed, approved and mediated states stay separate. A supplier label or an adjacent signature file never upgrades trust by itself, and `--no-project-policy` stops an untrusted checkout from choosing its own gates.
5. **Standards first.** One native inventory exports to CycloneDX 1.7, SPDX 3.0.1, SARIF 2.1.0 and VEX. Standard exports carry the full native inventory in a digest-bound extension, so a consumer that keeps it loses nothing.

When a supplier gives you an inventory and you have the corresponding checkout,
use both commands against the same project root.

```sh
nexus-symbiote validate inventory.json --project /reviewed/checkout --no-project-policy
nexus-symbiote risk inventory.json --project /reviewed/checkout --no-project-policy --json-output
```

Project reconciliation reruns the supported static collectors and compares
their security-relevant fields and findings with the supplied BOM, together with
the repository agent's profile and references and every relationship between
locally collected components. It needs at least one local subject. A supplied
component or relationship the checkout cannot corroborate fails reconciliation
when it claims local provenance, verified assurance or internal-verified trust;
otherwise it is listed as a supplier claim and the basis becomes
`project-reconciled-with-supplier-claims`. A claim the supplier adds to a locally
collected component, including one in place of a claim the collector could not
make, is listed the same way and fails when it asserts verified assurance. A
mismatch makes `validate` report the basis `project-reconciliation-failed` and
makes the project-backed risk command exit unsuccessfully with that basis, an
unknown risk level and a null score. Without a project, `risk` scores the supplied claims
and labels the result `supplied-bom`. For an operator-configured signature
check, supply the trusted signer policy when validating the project. In the
GitHub Action, pass it with the `signature-policy` input as a caller-owned file
outside the workspace; the Action verifies against the Sigstore trust root
embedded in its hash-locked runtime, not a runner cache.

A mediated action needs a trusted approver, snapshot binding, authenticated workload and endpoint, action/resource constraints, validity, current revocation state, rollback protection, and any action-specific approval. One-use approval must bind to the action and arguments it authorizes. Adapter checks cannot govern tools invoked through an unmediated route; deployments need their own network, identity, and sandbox controls to make mediation complete.

For hosted models, an alias is a locator. Provider-reported revisions and behavioral canaries do not establish measured weight identity. Preserve identity assurance and unknowns explicitly. For retrieval and memory, record the source and index versions, effective reader/writer permissions, and derived records requiring invalidation after withdrawal.

## Known false-positive and false-negative classes

These are current behaviors, not guarantees. Review them before relying on a gate. They explain how findings are classified; what the collectors do not record or verify is in the [known limitations](known-limitations.md).

- **Model format by extension.** `.pkl`, `.pickle`, `.pck`, `.dill`, `.pt`, `.pth`, `.bin`, `.joblib`, `.ckpt` and `.pdparams`, also inside an archive or compression suffix such as `.pth.tar` or `.pkl.gz`, are rated as potentially code-executing on file name alone, whether or not the content can be read. A non-pickle `.bin` file (firmware, game data) is therefore a critical finding, which fails the default gate. Formats with no structural validator (`.onnx`, `.gguf`, `.ggml`, `.h5`, `.hdf5`, `.keras`, `.tflite`, `.mlmodel`, `.pte` and TensorFlow's `saved_model.pb`) are reported as unknown, not safe, unless their content is a recognized pickle or torch archive, or a GGUF chat template reaches Python internals; a chat template configured in the model's directory that does adds a critical finding and leaves the rating unknown. Files outside these lists are not inventoried ([known limitations](known-limitations.md#models)). See [model integrity](model-integrity.md).
- **Risk score scale.** The aggregate score is the uncapped sum of finding weights (critical 10, high 7, medium 4, low 1, info 0). It grows with inventory size and is not a percentage. `risk --json-output` records that as `gate.score_scale` = `unbounded-sum`. The Action's `risk-threshold` input still accepts only 0 to 100, which is a threshold for that sum, not a bound on it. Low findings add up too: without `NEXUS_SYMBIOTE_SOURCE_BINDING_KEY`, each record with unbound values adds 1 ([known limitations](known-limitations.md#mcp-servers-and-tools)). The built-in CLI policy fails on any critical finding regardless of the aggregate. The Action's `fail-on-severity` input defaults to `high`, so high findings fail an Action run on their own. The Action's `risk-threshold: '0'`, like `risk --no-score-threshold`, removes only the score threshold: findings at or above `fail-on-severity`, unverified SafeTensors, incomplete coverage and missing evidence still fail the gate. The [finding catalog](finding-catalog.md) lists every category with its severity.
- **Free-text redaction.** Redaction removes known secret values; `name=value` and `name: value` pairs, with the name optionally quoted and the value up to whitespace, `,` or `;` or a whole quoted string, in which a backslash escapes the next character, whose name contains `api_key`, `access_key`, `secret_key`, `private_key`, `account_key`, `token`, `password`, `passwd`, `passphrase`, `pwd`, `secret`, `credential` or `sig`, directly or followed by digits or by up to four `-`, `_` or `.` delimited parts (`DB_PASSWORD_PROD=`, `token2=`), but not followed by letters (`max_tokens=`, `tokenizer=`); the credential after `Bearer`, `Token`, `Bot`, `ApiKey` or `Api-Key` when it has at least 16 characters, or at least six with a digit, punctuation, or both lower- and upper-case letters with an upper-case one after the first character (prose such as `Bearer authentication` survives), and after `Basic` when it decodes to a `user:password` pair; whatever its shape, the value after any of these schemes, or after `Negotiate` or `NTLM`, when it follows an `Authorization` or `Proxy-Authorization` header name (`Authorization: Basic ...`, `"Authorization": "Bearer ...`, `authorization=Token ...`, `Authorization: Negotiate ...`); PEM private key blocks; and tokens in known formats (JWTs and `ghp_`, `gho_`, `ghu_`, `ghs_`, `ghr_`, `github_pat_`, `glpat-`, `xox`, `sk-`, Stripe live and test keys, `AKIA`, `ASIA`, `AIza`, `ya29.`, `npm_`, `pypi-` and `hf_` prefixes), which all but JWTs and `sk-` keys are also found after `_` or `-` inside a name (`AWS_AKIA...`, `X_glpat-...`). Names compared with live evidence, such as server and tool names, get only the URL, assignment and scheme rules and those in-name token formats, so `sk-learn-classifier` stays a name. Credentials in other shapes are not recognized by pattern. MCP configuration scrubs a server's environment and header values from its free text only when the variable name marks a credential (it contains `KEY`, `TOKEN`, `SECRET`, `PASS`, `PWD`, `CREDENTIAL`, `AUTH`, `COOKIE`, `SESSION`, `PRIVATE`, `SIGNATURE`, `CERT`, `DSN`, `JWT`, `BEARER`, `HEADER`, `PAT` as a word, or a connection-string name) or the value has a known token format or URL user information, and the value has at least eight characters; such a value that occurs in a server name, tool name, command, package reference, package source or endpoint origin withholds that field and is a coverage gap. In free text a URL ends at whitespace, a quote or an angle bracket; `scheme://` URLs keep only their scheme, host and port, and one without a host, or whose authority holds a backslash, which browsers read as the end of the host, is replaced entirely. A dependency declared as a direct URL or VCS reference is redacted from the URL its requirement parses to, so it is recorded without its path, revision or query, and a change within the same origin (scheme, host and port) does not show in `diff`. A reference written without `//`, such as `file:/path`, or a relative path is recorded as written.
- **Hard links.** A hard-linked file inside the scanned root is collected like any other regular file and no failure is recorded: confinement is descriptor-relative and follows only a relative symlink to a regular file or directory in the project other than its root, resolved lexically without another symlink, but it does not establish inode provenance. A refusal would also fail legitimate deduplicated trees (`uv` and conda environments, Nix and Guix stores, `cp -al` mirrors). The [security boundaries](../SECURITY.md#security-boundaries) say how to run collection safely.
- **Hosted CI.** A configured workflow is not evidence that it ran; see `docs/repository-controls.md`.
- **Hidden characters.** The `prompt` collector reports every format character (Unicode category Cf), variation selector and blank filler, such as U+180E and U+3164, and every code point that Unicode reserves as default-ignorable without assigning it (U+2065, U+FFF0 to U+FFF8, U+E0080 to U+E00FF and U+E01F0 to U+E0FFF): bidi embeddings, overrides and isolates, tag characters and those unassigned code points of plane 14 as critical, the directional marks LRM, RLM and ALM as medium, and the others as high. A zero-width joiner between pictographs, a presentation selector (U+FE0E or U+FE0F) after a pictograph, a keycap base or another symbol in U+2000 to U+2BFF or U+3000 to U+32FF, the England, Scotland and Wales flag sequences and a byte-order mark that starts the text are not reported; pictographs are recognized by code-point ranges. Ordinary text can therefore raise findings: right-to-left text uses directional marks, a medium finding, and the joiners and variation selectors that Persian, Indic or Mongolian text uses are high findings. HTML and Markdown comments are a low `hidden_markup` finding, reported by count, in Markdown files and in instruction files without a suffix.
- **Unsupported surfaces.** A surface no collector reads is not a coverage gap, so gates pass and `diff` reports no change when it changes. A value the inventory binds only with `NEXUS_SYMBIOTE_SOURCE_BINDING_KEY` raises no alert without the key. The [known limitations](known-limitations.md) list both, and which records then carry a low `completeness` risk that names the key.

## What results do and do not establish

A successful scan is an inventory result. It does not establish that a model is benign, that a tool backend obeys its description, or that every agent action was mediated. Inspect the exit status and the inventory's coverage, exclusions and failures: a command may write evidence and still return a failing gate, and exit code `0` for informational commands, report-only output and skipped gates does not establish approval.

Collection is static by default and does not execute project modules, model loaders, hooks or MCP launch commands. A completed search can find no matching files. Failed reads and the unsupported declarations a collector recognizes remain coverage gaps, but some declaration forms and file types are skipped without a gap (see the [known limitations](known-limitations.md)), and collectors omitted from `--scanner` remain unknown. The `registry` collector reads every `requirements*.txt` in the project root, matching names without regard to case (a name with undecodable bytes or a control or format character is reported as a gap and not read), by pip 26.3's parsing rules, and does not follow includes, constraints files, editable installs or the targets of URL, VCS and path references. Each of these is a coverage gap or failure: an include, constraints file or editable install that reaches beyond the root requirements files or the project itself; a requirement that pip installs from a URL, VCS reference, archive or local path instead of by a package name, other than the project itself, or a `name @ URL` line whose text, read as a path, leaves the project root or starts with one of its entries (other `name @ URL` lines are recorded under their name and URL origin without a gap); an option pip 26.3 does not know on an option line; a `${NAME}` variable in a requirement's name or in an option line's option place (options after a requirement, other than `-e`, are not checked); and a declared encoding other than UTF-8. pip expands `${NAME}` variables before it splits a line, so a variable inside an option's value is not resolved or reported, and a value containing spaces could add options, including an include. A named `name @ URL` reference is recorded with its URL origin only, or as written when the URL has no `//`; a line that cannot be parsed is recorded only up to the word that holds its first `//`. A bare archive or directory path that starts with an AI package name is still also parsed as a requirement, so besides its coverage gap it can be recorded under a mangled name or reported as an invalid requirement. Dockerfile `FROM` instructions are read by BuildKit's default frontend rules, including continued lines, heredocs and build stages, and an image that BuildKit would resolve differently (an ARG substitution, quotes or escapes) is a gap. Configuration presence does not prove that a server is running or that its live tool definitions match the declaration. `verify-live` is a separate explicit execution operation requiring an independently pinned launcher policy and external isolation, and `discover-mcp` is an explicit HTTPS observation operation. Neither calls tools.

For trusted local projects, standalone `scan` loads project policy from the scanned directory, and `validate` and `risk` from the directory named with `--project`. Without `--project` they use the built-in policy and name any `.nexus-symbiote.yaml` they did not apply, because an inventory file can be written anywhere, including shared directories. A policy file in a parent directory, or beside an inventory file, is never consulted. Pass `--no-project-policy` when the scanned checkout must not choose your verification policy. When a project policy is honored, `validate` names its source, `risk` records it as `policy_source` and `scan` writes it into the inventory's metadata, with every relaxation of the built-in gates, and every setting that changes reported results, listed under `policy_weakened` and, in human-readable output, warned about on stderr, so a switched-off gate is a visible choice rather than a silent one. The [policy reference](policy-reference.md) lists every setting. Standalone ShadowScan imports require a new output path and retain partial coverage; `--report-only` is an explicit inspection mode. Imported discovery remains a source claim and does not establish deployment, effective access or authorization.

| Capability | Evidence and limitation |
| --- | --- |
| ShadowScan integration | Exact source-report digest for authentication and a normalized content digest for drift, mapped components and supported declared edges, with unmapped indexes and projection limits. The producer is authenticated only by `verify-discovery --bundle` for a BOM written by `import-shadowscan`, or, for a merged `scan` BOM, when `validate` or `risk` runs with `--project` and an operator signature policy entry for the report verifies (`validate.require_discovery_signature` makes that entry mandatory); the check authenticates the producer, not the report's commit or time; no trust upgrade |
| MCP and tools | Scoped client/server references and supported source declarations; runtime descriptors and backend behavior need separate evidence |
| Model integrity | Whole-file hashes of every weight file (including ONNX external data, SavedModel variables and shard indexes), digests of configuration, tokenizer, chat templates and declared custom code, bounded format inspection, SafeTensors metadata fingerprints, and operator Sigstore signatures or digest pins; a format, header fingerprint, pin or signature does not prove benignness |
| Instructions and skills | Source-bound artifacts and suspicious-content findings; detection is limited to supported files and patterns |
| Retrieval and registries | Declared configuration, package identities and lineage references; presence does not establish actual installation or retrieval ACL enforcement |
| A2A and IDE declarations | Agent Cards, host settings and extension declarations; supplier labels are not proof of endpoint identity, execution or signature validity, and the `security` or `securityRequirements` that a card or its skills declare are not proof that the endpoint enforces them |
| Runtime contracts | Ed25519-signed snapshots, approvals and trust status bound to authenticated context in a reference adapter; deployments must prevent bypass and protect state |
| Impact analysis | Potential graph reachability through recorded relationships, not proof that an exploit executed |
| Graph view | Risk classes and exposure paths restate recorded evidence and associations; they do not establish what a component does at run time, effective authority or exploitability, and an unclassified component is unknown, not safe ([graph view](graph-view.md#what-the-view-shows-and-does-not-show)) |
| Content digest | Two inventories record the same content apart from when and in which run each was collected; not who produced either file ([reproducible inventories](reproducible-inventories.md#the-content-digest)) |
| Inventory attestation | Trusted keys signed these bytes, or this inventory content, for this purpose, at a signing time the signer's clock gives; not that the inventory is accurate, complete or safe, or that it is the newest one ([inventory attestation](inventory-attestation.md#what-an-attestation-establishes)) |
| Trace evidence | What the agent's own instrumentation reported, matched by name and reported endpoint and recorded as `reported`; it never raises a component's assurance, and a missing span proves nothing ([trace evidence](trace-evidence.md#trust-model-reported-not-observed)) |
| Framework crosswalk | That a finding records a precondition, a weakness or evidence relevant to a framework entry; never that an attack happened, that a control fails or that an obligation applies ([framework crosswalk](framework-crosswalk.md#what-a-reference-means)) |
| G7 minimum elements | Which elements the CycloneDX export carries in standard fields, with the ratio's denominator; coverage, not compliance, and no value is verified ([G7 minimum elements](minimum-elements.md#limits)) |
| ShadowScan approved inventory | The reviewed repository agent approved for one resource in ShadowScan's reconciliation; not that the prefix names the reviewed repository, nor anything about the content there ([ShadowScan approval](shadowscan-inventory-export.md#what-the-export-does-not-establish)) |
| GitHub Action | One collected inventory, caller-owned gates and signer policy, and optional SARIF upload; a gate an input disables is printed as a warning and reported as `skipped` in the `gates` output; on `pull_request` the workflow file belongs to the pull request ([known limitations](known-limitations.md#github-action)) |

Project validation compares static MCP and A2A records and configured tool fingerprints with fresh local evidence. A structure binding detects added or removed arguments, environment variables, headers, resolver settings and tools, and changed launchers, package identities, versions and pins, package source origins (including project `.npmrc`, `bunfig.toml`, `.yarnrc.yml` and `uv.toml` registries), launch context and endpoint origins. With `NEXUS_SYMBIOTE_SOURCE_BINDING_KEY` set, a keyed binding also detects same-version package swaps and changed argument, environment, header, endpoint, index and resolver setting values, without exporting anything a secret could be guessed from. Without the key, MCP records carry a low completeness risk that names it. Tool `definition_hash` values are an exception: they are unkeyed digests of the original declared descriptor, so a low-entropy value that the exported descriptor omits can be confirmed by guessing. A2A records export OAuth scopes and URL origins in clear and carry unkeyed structure digests over top-level field names, counts, URL shapes and the requirement alternatives of each card and its skills, including the requirement values of schemes other than OAuth 2.0 and OpenID Connect, so anyone holding the BOM can confirm guesses of those values. With the key, they also carry an HMAC over the whole card or client entry, which detects same-host path, tenant and token URL changes; without it, records with unbound URLs, tenants or redacted scopes carry a low completeness risk. RAG sources carry the same pair: an unkeyed structure digest and, with the key, an HMAC over the declaration. IDE settings files carry a digest of each file's redacted form (`settings_hashes`, profile `settings_hashes_profile`), with or without the key, so no unkeyed digest covers a settings `env` value or an `apiKeyHelper` command, and, with the key, an HMAC over every file as read. A memory file's import of a file that is not Markdown, or of a name that a symlink resolves to such a file, carries no unkeyed content digest; with the key, it carries an HMAC over its text, which project validation recomputes. MCP references include the relative configuration path and declared name. Legacy snapshots without the binding, or with name-only identities, need recollection; see [source reconciliation and migration](verification-source-binding.md). Python, TypeScript and JavaScript source declarations are collected only from files that name the MCP SDK or, for Python, a supported agent framework, outside test, build, documentation, benchmark and example directories, and within the [collection limits](collection-limits.md); unresolved or dynamic registrations, constructor-supplied tools, low-level servers, decorators on imported servers, SDK imports in a parsed file that the analysis cannot follow, dynamic imports of the SDK and servers that application code starts or reaches are reported as gaps; the [known limitations](known-limitations.md#mcp-servers-and-tools) list the forms that leave none.

CycloneDX 1.7 and SPDX 3.0.1 exports use supported standard structures and a digest-bound native extension. Consumers must retain that extension to recover full native semantics and inspect the selected-field loss report. Without the extension, standard fields still guarantee two things. First, a conditional edge never appears as a typed, unconditional relationship: CycloneDX leaves it out of the dependency graph, and SPDX exports it as `other` with a `comment` that names the native relationship and states the condition. Every other SPDX `other` relationship names its native relationship in a `comment`. Second, coverage is never `complete`: the CycloneDX `compositions` aggregate and the SPDX relationship `completeness` are `incomplete` for scoped, failed, excluded or imported collection, including a claim that carries any imported-discovery field without a report digest, and otherwise `unknown` or `noAssertion`. Which collectors ran, what failed and what was excluded remain extension-only. Each export declares the projection version that produced its standard fields, and recovery rejects any standard field that disagrees with the embedded native document under that projection, apart from the exact historical edge projection that `allow_legacy_relationships` accepts for exports without a version; exports from builds before 0.1.0 may need to be regenerated, and a CycloneDX reader that drops an `incomplete` composition, as cyclonedx-python-lib does when it reserializes, leaves a document that no longer recovers. A digest detects changes; it does not authenticate the producer. SPDX identities are scoped to each inventory revision. SARIF contains reviewable findings rather than an admission decision; it marks a run with a collection failure as unsuccessful, and standalone ShadowScan imports do not support SARIF. [Standard exports](standard-exports.md) maps every field. VEX output marks findings `in_triage` and does not assert exploitability. Schema validity alone establishes neither semantic equivalence nor complete collection.

Inventories can expose infrastructure, permissions, source references and instruction fingerprints. Restrict evidence access and retention, and review artifacts before sharing them. Use independent expected digests and signer/issuer policies; a signature or registry label does not establish content safety. IDE permission records describe collected project declarations: Claude's `permissions.defaultMode`, the blanket grants in its allow list, how many allow, ask and deny rules and hook handlers it declares, findings for hooks and other risky settings, and a digest of each settings file's redacted form are retained; with `NEXUS_SYMBIOTE_SOURCE_BINDING_KEY` an HMAC under the key also binds every value. The rules and hook commands themselves are not recorded (see the [known limitations](known-limitations.md#instructions-and-ide-settings)), and user/managed policy, workspace trust and session flags remain outside effective-authorization verification. Scanner failures emit application-owned diagnostic codes; raw exception text and invalid model configuration values are omitted from failure reports. `--debug` prints the class and code locations of a collector or internal error, never its message.

The security and inventory benchmark corpora are finite regression cases. They establish no representative field accuracy, complete collection or percentile ranking.
